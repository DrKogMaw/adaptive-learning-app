# Next Step — adaptive learning prototype

This repository is an eight-step web application prototype for introductory JavaScript. It has a 20-topic prerequisite graph, a versioned feasibility experiment, six study cycles with alternate pre, immediate, and delayed checks, an optional cognitive task battery, a pilot quality dashboard, and an optional account in the local .NET app.

## Run the app

Install .NET SDK 10. From this folder:

```powershell
dotnet run --project api/NextStep.Api.csproj --urls http://127.0.0.1:5080
```

Open <http://127.0.0.1:5080>. SQLite is the default for local development. On first launch, EF Core creates `api/nextstep-dev.db` and the account tables. To choose another local file, set `NEXTSTEP_SQLITE_PATH` to an absolute path before running.

For a **fresh, empty PostgreSQL database**, set `NEXTSTEP_DB_PROVIDER=postgres` and `NEXTSTEP_POSTGRES_CONNECTION` to a PostgreSQL connection string, then run the same command. The API creates its Identity, study, cognitive, and recommendation tables on first launch. Existing Step 4 or Step 5 databases receive the later tables automatically. Use HTTPS and a persistent ASP.NET Core Data Protection key ring before exposing the API beyond local development. This prototype still uses `EnsureCreated` plus focused upgrades rather than a general migration system; do not point it at an unrelated database or one containing the older `schema.sql` draft.

`node serve.mjs` runs the browser-only version without accounts or database storage. The private hosted Sites preview is also browser-only because Sites hosts static files, not the .NET API. The cognitive assessment works in both modes; completed browser-only runs stay on that device.

## Step 4: accounts and storage

In the local .NET app, create an account or sign in, read and accept the versioned consent notice, then choose **Use this browser's progress** or **Load account progress**. After that choice, changes in that browser save to the database automatically. The account panel can export stored progress, withdraw consent, sign out, and delete the account and server data. Withdrawing consent stops new writes but leaves existing data available for export or deletion.

The API stores learner settings, study sessions, attempts, and individual item responses in separate tables. It recalculates attempt scores from the server's item bank during import and scopes reads and writes to the signed-in account. Cookie authentication uses same-origin requests and antiforgery tokens for account data changes. Existing browser-only progress is never uploaded before the learner explicitly chooses it.

The `schema.sql` file is an earlier research-oriented design for later cognitive tasks and experiments. The executable Step 4 tables are defined in `api/Data.cs` and generated by EF Core. It is not a migration script for this version.

## Step 5: cognitive tasks and personal reference

The optional assessment has 12 vigilance trials, 8 backward digit sequences, 20 flanker trials, 24 number-rule switching trials, and a six-answer state questionnaire. Stimuli are randomized from a saved seed. Each completed trial records its task version, stimulus, response, condition, timing, and correctness. If the tab is hidden, the unfinished run is discarded; only completed runs are saved.

Run 1 is practice. Runs 2 and 3 form a preliminary personal reference for the same battery version. Run 4 onward shows descriptive differences from that reference. The displayed summaries use median response times and task accuracy, with lapses, false starts, and response-time differences where enough correct trials are available. No cognitive trait or diagnosis is inferred, and these results do not change the topic recommendation.

The local .NET API stores completed cognitive sessions, individual trials, and questionnaires in separate tables. It validates task versions and structure and recalculates correctness from stored stimuli and responses. Response times and timestamps still originate in the browser.

## Step 6: strong baseline recommendation policy

The deterministic `baseline-1.0` policy first removes topics whose prerequisites are not confident. It ranks the remaining topics using delayed reviews that are due, continuity for active study cycles, time fit, goal match, an evidence based mastery estimate, topic difficulty, and measurement uncertainty. The recommendation card shows the priority, mastery estimate, uncertainty, and up to three eligible alternatives. Learners can still choose any topic.

The priority is a transparent planning score, not a predicted learning gain. Cognitive assessment results are intentionally excluded so later experiments can compare cognitive models with a meaningful educational baseline. The browser saves versioned recommendation records with the chosen topic, candidate count, factor breakdown, selection probability, and whether the learner started it. The local .NET account stores and exports those records in a separate `Recommendations` table.

## Step 7: feasibility experiment

Each browser receives one stable 50/50 assignment to `baseline` or `randomized-eligible` under experiment version `feasibility-1.0`. The baseline policy selects its highest priority eligible topic. The comparison policy uses a deterministic draw among prerequisite-ready topics, records a `1 / candidate count` selection probability, and stays stable for the same assignment and learning context. The interface identifies the assigned policy and preserves the learner's ability to choose another topic.

Versioned research events record assignment, recommendation exposure and acceptance, study starts, completed assessments, learner setting changes, and resets. Account storage enforces one immutable assignment and append-only event IDs. Cognitive results remain excluded from topic selection until a separately specified and validated policy is ready.

The consent notice is version `2026-10-11-v4`; existing accounts must accept it before saving the pilot assignment and interaction events to the server.

## Step 8: pilot quality and analysis readiness

The personal pilot dashboard summarizes study-cycle completeness, due delayed reviews, recommendation acceptance and overrides, cognitive-run coverage, recorded study duration, practice change, and descriptive consistency between cognitive reference runs. It can export one row per study session as CSV without account identifiers.

The frozen `pilot-analysis-1.0` plan defines feasibility measures, quality flags, version-freeze requirements, and the gate for a later powered study. These checks describe whether data collection is usable; they do not estimate policy effects or establish educational benefit. A cross-user pilot still requires participant recruitment, research review, and cohort-level analysis outside the browser-only hosted preview.

## Current limits

- The hosted preview still keeps all progress in that browser. Accounts and PostgreSQL require running/deploying the .NET API separately.
- Learning progress is copied as a snapshot. Assignment and event history are preserved by the API, but concurrent use in multiple browsers is not yet supported; load the account copy before switching devices.
- Historical browser timestamps and response times are client supplied. Knowledge and cognitive correctness are recalculated, but timing is not independently verified.
- The short question forms and cognitive tasks are not calibrated. Pre/post differences are not validated learning gains; the short battery is not a reliable diagnostic measure of a stable cognitive trait.
- Topic mastery and uncertainty are preliminary estimates from short, uncalibrated forms plus a weak status prior. Use them for planning and pilot evaluation only.
- Consent language is a product prototype, not a formal research consent document. A real participant study needs review of consent, retention, security, and measurement procedures.
